## 1. 结论先行

**项目定位**：本地语料的 RAG 对话系统，核心是一条检索质量门控闭环——检索结果先过
reranker 过滤相关性，再过 LLM judge 判断"够不够回答问题"，不合格走策略池
（查询重写 / 切混合检索 / 拒答），最多重试 3 次，仍不合格则诚实拒答。

**命名与对外描述**：仓库名 `corrective-rag`。简历和面试一律用论文原名——
"基于 CRAG 式纠错循环（arXiv:2401.15884）与 Adaptive-RAG 查询路由（arXiv:2403.14403）的
RAG 系统"。不自称 Agentic RAG：那是伞术语（综述 arXiv:2501.09136，2025），底下装着
reflection / planning / tool use 一整套模式，本系统只实现其中两类，背伞被追问定义就失分。

**与原始方案的关系**：六模块骨架保留，五处修正——
1. "Agent 节点"正名为 query router（它就是个二分类器，Adaptive-RAG 的 classifier，不是 agent）；
2. 评分节点拆成 reranker + LLM judge 两层（相关性用 cross-encoder，充分性才用 LLM）；
3. 纠错从"只会重写查询"扩成策略池（重写 / 切混合检索 / 拒答），CRAG 原文也是三态纠错 + web 兜底；
4. 补 abstain 终态和 max_iterations（原状态机画了个死循环，没有出口）；
5. 评测改用公开中文基准（DuReader-retrieval + RGB），放弃自建标注集——标注工时不可压缩，
   且公开人工标注 + 论文可比基线比自建 100 条更硬；协议纪律取代"标注质量"成为新风险点。

**最大风险不是技术，是评测协议**：公开基准把"标注工时"风险换成了"数据污染 + 口径说不清"
风险（第 5、9 节）。Phase 2（baseline 数字）仍然优先于 Phase 3。

## 3. 技术栈定稿（含对原方案的偏离理由）

| 组件 | 选型 | 理由 |
|---|---|---|
| 编排 | **LangGraph 单独用**，不装 langchain 全栈 | 状态机 + 条件边 + checkpointer 正好表达纠错循环；LangChain 抽象层版本 churn 大，面试讲不清依赖反而失分 |
| 向量检索 | **FAISS**（IndexFlatIP + L2 归一化 = 精确余弦），自写 30 行持久化 | 零版本意外、完全可讲清；chroma 弃用原因：默认 embedding function 会偷偷调 OpenAI API，必须显式覆盖才安全 |
| Embedding | BAAI/bge-small-zh-v1.5（约 100MB，512 维） | 中文效果好、体积小；**query 侧必须加指令前缀**（官方 README 约定，漏加掉点） |
| Reranker | BAAI/bge-reranker-base（CPU） | 相关性过滤比 LLM 便宜且稳；不够再换 bge-reranker-v2-m3 |
| LLM | **小米 MiMo API**（mimo-v2.6-flash，openai SDK，OpenAI 兼容协议） | 实测：key 有效、普通推理 + `response_format` json_object 均可用；国内定价输入 ¥1.00 / 输出 ¥2.00 每百万 tokens（cache 命中 ¥0.02），按量付费适合有限余额；换供应商只改 `.env` 三行不动代码 |
| 切分 | **自写**递归切分（`src/corrective_rag/chunking.py`，已实现并跑通冒烟） | 中文分隔符优先级自己掌控；408 题都整理过的人写得来这个 |
| 评测 | **自写 judge 脚本**（定义对齐 ragas 公开文档）+ 自研 JSONL trace | ragas 装不上：0.4.3/0.3.9 均 import 即炸（依赖 langchain-community 的 vertexai 模块，0.4.2 已删除；降级会连带 langchain-core 威胁 langgraph）。四个指标本就是 LLM judge 口径，自写完全可控，命名对齐行业黑话 |
| 前端 | gradio（streamlit 亦可） | 聊天 demo 最省事 |
| trace | 自写 JSONL，不引 LangSmith | 免账号、免外网、数据在本机 |

## 5. 语料与评测集（2026-10-12 决策变更：公开基准优先）

**决策：放弃自建标注集，改用公开中文基准。** 理由：标注工时是整个项目最不可压缩的
部分；公开基准带人工标注的 ground truth，还有论文公布的可比基线——面试语境下
"DuReader-retrieval test split"比"我自己标了 100 条"更硬。

**三个已核验的基准**：

| 基准 | 管什么 | 关键事实（2026-10-12 查证） |
|---|---|---|
| DuReader-retrieval（arXiv:2203.10232，百度） | 检索层 | **人工标注**（多检索器 pooling + 人工复核，平均 4.9 相关/query），train 为远监督。HF 打包版实测：2,000 queries / 100,001 passages / 9,839 条二值 qrels（论文 dev 数字为 9,863 passages，MTEB 打包池更大）。论文基线：BM25 MRR@10 **21.03** → 双编码器 **53.96** → +cross-encoder **74.21** |
| C-MTEB/DuRetrieval | 同上，MTEB 打包版 | HF 格式；经 hf-mirror + datasets **实测下载成功**。关键结构：queries/corpus 在主 repo，**qrels 在单独 repo `C-MTEB/DuRetrieval-qrels`**（不看文件列表发现不了，漏了它整个评测无从谈起）；MTEB 包只含 dev 部分，论文所说 test 4,000 不在其中 |
| RGB（arXiv:2309.01431，AAAI 2024，中科院） | 生成层 | 中英双语，四大能力：噪声鲁棒 / 负例拒绝 / 信息整合 / 反事实鲁棒——**一一对应纠错循环的四个策略**。注意：基于 2022-2023 新闻构建，LLM 参数化知识可能已记住部分内容，负例拒绝成绩要打折解读 |

**分工设计**：DuRetrieval 管"检索 + 相关性判断"——它的 qrels 是真人标注，
judge 一致性拿它验，比自标强；RGB 管"拒答 + 抗噪"——四大能力正好测策略池的四个分支。

**协议纪律**：
- dev split 调参（reranker 阈值、judge 阈值），**test split 只跑一次最终 A/B**；
- 论文基线数字（21.03 / 53.96 / 74.21）可引用作对照锚点；
- **污染披露**：bge-small-zh-v1.5（2023）与这些基准（2022-2023）时间线重叠，可能存在
  训练数据污染 → A/B 的 delta 比绝对值可信，简历面试主动说这条，说了是加分；
- demo 语料 = 基准自带 passage pool（顺带解决"demo 搜什么"）；个人 md 语料降为可选。

## 6. 指标定义（每个数字的算法，杜绝"提升了效果"）

| 指标 | 算法 | 来源 |
|---|---|---|
| 答案可用率 | A+B 类中"含标准答案要点且无编造内容"的比例（LLM judge 初判 + 人工抽 20% 校准） | 自研 |
| 离题率 | 答案与问题无关的比例（同上的补集） | 自研 |
| 拒答恰当率 | C 类拒答的比例 与 A+B 类误拒的比例，分开报，不合并成一个数 | 自研 |
| Recall@10/@20、hit@k | DuRetrieval qrels 为二值相关，标准 nDCG 会退化；报 Recall@k 与 hit@k | 自研 |
| faithfulness / answer relevancy / context precision / context recall | 自写 judge 脚本，定义对齐 ragas 公开文档；当前 key 预算下 judge 与生成同用 MiMo（**同源**）——边界：judge 评的是检索文档而非模型自产内容，同源自评偏差主要发生在 self-reflection 场景，RAG judge 场景风险小得多，面试主动披露 | 自研（ragas 装不上，见第 3 节） |
| 平均重写次数 / 重试触发率 | trace 统计 | 自研 |
| p50 端到端延迟、token/query | trace 统计 | 自研 |
| judge 一致性 | judge 的 0/1/2 与 DuRetrieval 的人工 qrels 算 agreement | 自研 |

- A/B 口径：同一 test split（DuRetrieval test，只跑一次），naive（单趟 top-k 直生）
  vs corrective（全闭环），报告写成 "X% → Y%"，不写"提升了 XX"。
- judge 一致性低于 75% 先修 prompt，再动系统。（75% 是自定目标，非行业标准，注明。）

### Phase 1 · naive RAG —— 目标：10 个问题有答案有引用（**已完成 2026-10-13**，冒烟实测 top1 命中、stub 链路通）

- 动作：`ingest.py`（md → 切分 → bge 向量化 → faiss 落盘）→ `retrieve.py`（top-k）→
  `generate.py`（MiMo，prompt 强制要求引用 `[chunk N]`）。
- 无 API key 时先加 `--stub-llm` 开关（返回假答案），验证检索链路。
- **验收**：CLI 问 10 个问题，人工核对每个引用 chunk 打开确实支撑答案。
- 已知 cosmetic 问题：切分会产生少量"纯小标题"短 chunk（如 20-30 字符），
  Phase 1 末尾加一步清洗：丢弃 < 30 字符且是邻居子集的 chunk。
- **产出对应简历**："实现了从文档加载到答案生成的全链路，答案强制携带可核对引用"。

### Phase 2 · 评测 harness + baseline —— 目标：baseline 数字落盘（**已完成 2026-10-13**：Recall@10=80.5%、MRR@10=87.8%、hit@1=82.6%，2,000 条 27 秒）

- 动作：下载 DuRetrieval（dev split）+ RGB 中文子集 → `data_loader.py` 转 jsonl →
  `trace.py` → 自写 judge 指标脚本 → baseline 报告 JSON。
- **验收**：naive 版在 test split 上的全部指标产出并落盘。
  **没这组数字不许进 Phase 3**——没有 baseline，纠错循环的提升无法证明。
- **产出对应简历/面试**：所有量化数字的 baseline 来源；面试问"你怎么证明有效"的第一张牌。

### Phase 3 · 质量门控 —— 目标：judge 可信（**代码已完成 2026-10-13**：reranker 增益实测 +8.4pp、校准发现分数饱和、LLM judge 接 MiMo、成本核算；judge 一致率评测进行中）

- 动作：`retrieve.py` 改为 top20 粗排 → `reranker` 精选 top4；
  `judge.py` 结构化输出 `{relevance: 0/1/2, sufficient: bool, reason}`；
  跑 judge vs DuRetrieval 人工 qrels 一致性。
- **验收**：agreement 报出（目标 ≥75%，自定）；reranker 前后 context precision 对比；
  单 query 成本/延迟前后对比（reranker 是 CPU 前向，应远便宜于 LLM）。
- **产出对应面试**："评分节点怎么设计的"完整答案：为什么 reranker 前置、
  为什么 0/1/2 而不是 1-10（LLM 打 1-10 分校准差，分布堆中间）、grader 误差率怎么估。

### Phase 4 · 纠错闭环 —— 目标：A/B 数字 + 拒答案例

- 动作：`graph.py` 画 LangGraph 图：

```
router ──直答──> generate
  │
  └──检索──> retrieve(20) ──> rerank(4) ──> judge
                                          │
              ┌───────────────────────────┼────────────────────┐
              ▼                           ▼                    ▼
          sufficient               relevance 低            超过 max_iter
              │                           │                    │
              ▼                           ▼                    ▼
          generate              策略池：查询重写/切BM25混合    abstain 拒答
                                          │
                                          └──> 回到 router（iterations+1）
```

  state 必须带 `iterations` 字段，`MAX_ITERATIONS=3` 封顶；每次流转写 trace。
- **验收**：corrective vs naive 的 A/B 报告（test split，一次）；≥5 个拒答案例人工检查"拒得对"；
  重写前后 query 的 drift 抽检（重写把"它"指代搞错的例子有没有）。
- **产出对应简历**："闭环检索架构：Agent 判断 → 检索 → LLM 评分 → 不通过则重写查询 →
  重新检索，无效检索的二次解决率从 X% 到 Y%"——注意这是 A/B 后的真实数字，不是恒真式。

### Phase 5 · 多轮对话 —— 目标：5 轮连贯追问

- 动作：`rewrite.py` 支持注入对话历史（condense question：把"那它的成本呢"结合历史
  改写成独立问题）；`memory.py` 滑动窗口（近 2-5 轮原文）+ 超窗部分 LLM 摘要；
  LangGraph checkpointer 存会话状态。
- **验收**：demo 连问 5 轮带指代的追问不散；token 对比数字
  （必须写明"第几轮、窗口多大下实测"——摘要本身也花 token，短历史可能负优化）。
- **产出对应简历**：多轮上下文管理那条 bullet 的数字来源。

### Phase 6 · 定稿 —— 目标：简历能写、demo 能放

- 动作：所有数字从 `data/traces/` 的 JSON 报告出；gradio demo；简历 bullet 定稿。
- **验收**：**每个 bullet 的数字都能在 JSON 报告里找到出处**。找不到出处的数字删掉。

## 9. 成本与风险预算

- **调用量估算（已实测单价）**：MiMo flash 输入 ¥1.00 / 输出 ¥2.00 每百万 tokens；
  20 条试水实测 **每 query ¥0.0046**（judge + generate 各一次调用，含重试）；
  300 条全量 A/B 预算 ≈ ¥1.4，全量 2,000 条 ≈ ¥9.2（时间成本 16 小时，不跑）。
  `cost.py` 逐条记账，trace 里可查每 query 花费。
- **防爆措施**：trace 逐条记 token；`.env` 可调 `MAX_ITERATIONS`；评测先 10 条 smoke 再全量。
- **最大风险已换位**：不再是标注工时，而是 (a) 数据污染（bge-small-zh 与基准时间线重叠，
  见第 5 节）；(b) 口径说不清（面试追问 nDCG vs Recall、qrels 二值、test 只跑一次）；
  (c) MiMo 余额有限（约 10 元）——实测单价下够跑 2,000 次 judge，但全量 2,000 条 A/B
  时间不允许，按 300 条规模规划。三条都已写进协议纪律，照做即免疫。

## 10. 简历 bullet 定稿写法（占位符只能填 Phase 6 实测数）

> 设计并实现了一个带检索质量门控的纠错式 RAG 对话系统（CRAG 式纠错循环 + Adaptive-RAG
> 查询路由），通过"reranker 相关性过滤 + LLM 充分性判断 + 策略池纠错"解决了传统 RAG
> 在检索结果不相关时仍强行生成的问题。

- **闭环检索架构**：基于 LangGraph 构建状态机，实现"查询路由 → 检索 → reranker → LLM 评分 →
  不通过则重写/切混合检索 → 重新检索"的反馈循环；在 DuReader-retrieval test split
  （4,000 条人工标注查询）上，答案可用率从单趟 RAG 的 X% 提升至 Y%，平均重写 1.x 次，
  p50 延迟 Z ms。（X/Y/Z 必须来自 test split A/B 报告）
- **质量门控设计**：设计 0/1/2 级相关性 + 充分性二分类的结构化 judge，与 DuReader-retrieval
  人工 qrels 一致性 XX%；相关性过滤前置 reranker 后，单 query LLM 调用成本下降约 X%。（X 来自 Phase 3 对比）
- **拒答与抗噪**：在 RGB 中文子集的负例拒绝/噪声鲁棒测试上，纠错循环的拒答恰当率
  从 X% 提升至 Y%。（X/Y 来自 test A/B；RGB 的参数知识污染已在面试话术中主动披露）
- **多轮上下文管理**：滑动窗口 + LLM 摘要两级策略 + 基于历史的查询改写，支持 5 轮以上
  连贯指代追问，在第 N 轮、窗口 M 轮配置下 token 消耗降低 X%。（X 必须写明测量点）

**禁用写法回顾**（都会被面试官当场问穿）：
- "二次成功率从 0% 提升至 XX%"——基线不重试所以恒为 0%，同义反复；
- "Token 消耗降低约 40%"——没有测量点的数字等于编的；
- "提升了效果"——没有对比对象的形容词。
